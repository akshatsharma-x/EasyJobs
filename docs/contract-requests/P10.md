# P10 · Internshala — contract requests

Nothing here blocks P10; each item has a working fallback inside `packages/scrapers/internshala`. For W1 (and P03/P05).

## 1. Let incremental scrapers opt out of sweeps (P05 / contract)

`internshala-internships` and `internshala-jobs` crawl newest-first and stop at the first page made entirely of known ids,
so a run that finishes without error still sees only the newest few hundred of ~12,000 postings. A sweep after such a run
would close almost everything.

- **Today:** we emit `target: null` and never rely on `/v1/ingest/sweep`. Closing comes from the §0.4 job-board rules
  (21 days unseen / 45 days old), `validThrough` (Internshala's apply-by date) and our refresh rotation (each run also
  re-reads 2 rotating deep pages, so a listed posting is re-seen every ~1–2 days).
- **Ask:** the worker must not sweep `(source, null)` for these scrapers. Suggested contract addition:
  `Scraper.sweep?: boolean` (default `true` for ATS scrapers, `false` here), or `ScrapeContext.markIncomplete()`.

## 2. Internshala URLs end with a timestamp, not an id (P03 `canonicalJobKey`)

`https://internshala.com/internship/detail/<slug><digits>` — the trailing 10 digits are the Unix time of the latest
(re)post. A repost changes the URL but keeps the posting id. The stable id is the card's `internshipId` attribute, which we
emit as `sourceJobId` and `extra.internshalaId`.

- **Ask:** if `canonicalJobKey` has an Internshala rule, don't treat the URL digits as the job id. internshala.com should be
  on the job-board host list, so fingerprints use §0.4 rule 2 (company | title | city | jobType).

## 3. Salary periods Internshala uses but `Salary.period` lacks (contract)

Internshala writes stipends `/week` and as a `lump sum` for the whole internship.

- **Today:** `/week` × 52/12 → `period: "month"`. A lump sum ÷ max(1, duration in months) → `period: "month"`, so short
  internships are never inflated. Without a duration a lump sum gives `salary: null`. `salary.raw` keeps the original text
  ("₹ 300 /week", "₹ 1,500 - 15,000 lump sum"), and `extra.payKind` / `extra.payPeriod` record what it was.
- **Ask (low priority):** add `"week"` to `Salary.period`, or a `Salary.basis: "lump_sum"` flag.

## 4. "Unpaid" is a known zero (P03 / P02 / P01)

Unpaid internships are emitted as `salary: { min: 0, max: 0, currency: "INR", period: "month", raw: "Unpaid" }` plus the tag
`unpaid`. "Performance Based" stipends are `salary: null` with `salaryRaw: "Performance Based"`.

- **Ask:** normalize should keep 0 as a real value (`salaryInrYearly* = 0`, not null), and the UI should show `salary.raw`
  ("Unpaid") instead of "₹0".

## 5. Free-form tags worth adding to `KNOWN_TAGS` (contract / P01)

Besides `wfh` and `women`, we emit `part-time`, `ppo` (pre-placement offer: "Job offer upto ₹ 5LPA post internship") and
`unpaid`. Ask: add them to `KNOWN_TAGS` (with labels) so the UI can offer them as filters.

## 6. Location string for work-from-home postings (P03)

WFH postings are emitted with `locations: ["Remote - India"]`, `workMode: "remote"`, `isRemote: true` (Internshala's JSON-LD
says `applicantLocationRequirements: IN`; its `jobLocation` for WFH posts is the employer's office, so we ignore it).
Ask: make sure `normalizeLocations("Remote - India")` gives `country: "IN"` with no city.

## 7. Tooling note for W1: pnpm 12 and build scripts

With pnpm 12.23, `pnpm --filter … add -D tsx vitest` ended with `ERR_PNPM_IGNORED_BUILDS` ("Ignored build scripts:
esbuild@0.28.2. Run pnpm approve-builds") even though the root `pnpm-workspace.yaml` lists esbuild under
`onlyBuiltDependencies`. The dependencies were still installed and recorded in the lockfile, and esbuild/tsx/vitest work
(esbuild ships its binary as an optional platform package). W1 may want to check which setting pnpm 12 expects for build
approvals so other sessions don't see the error.

Related observation (not caused by P10): at 03:34 local on 2026-11-26 another session's pnpm run rewrote the root
`pnpm-workspace.yaml`, adding a `minimumReleaseAgeExclude` list (vitest@5.1.2, @vitest/*, @scalar/*, hono@4.13.22). It
no longer matches §0.2 byte-for-byte; P10 did not touch it. W1 should decide whether to keep it.
