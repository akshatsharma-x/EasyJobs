# P07 contract requests (@easyjobs/scraper-ats-public)

Nothing here blocks P07 — each item has a working fallback today. Ordered by impact.

## 1. A cheap "seen" channel so ATS scrapers can honour `ctx.since` without breaking sweeps

**Problem.** The worker sweeps `(source, target)` after every complete run (§0.4, P05), closing every stored job
that was not emitted. An ATS scraper that honoured `ctx.since` would emit only new or updated postings, and the
sweep would then close every older open job. So P07 ignores `ctx.since` and emits each board in full on every
run (Databricks: 874 jobs every hour, mostly unchanged).

**Proposal (backward-compatible).** Add an optional callback to `ScrapeContext`:

```ts
/** Report postings that are still open but unchanged since ctx.since — counted as "seen" by the sweep. */
markSeen?: (sourceJobIds: string[], target?: string | null) => void;
```

The worker adds these ids to `seenSourceJobIds` without normalising or ingesting them. Scrapers that don't call
it keep today's behaviour.

## 2. `isKnown` should mean "stored *with* details" (or add `needsDetail`)

P07 emits light records (`descriptionHtml: null`) for known SmartRecruiters/BambooHR postings, as the contract
allows. If a posting is ever stored only as a light record, `isKnown` returns true forever and it never gets a
description. P07 avoids this by **deferring** unknown postings beyond its detail budget (`ATS_MAX_DETAILS`) or
after a 429, rather than emitting them light. Other scrapers may not, so either:

- define `isKnown(id)` as "stored and has a description" (cheap for P02: `description_html IS NOT NULL`), or
- add `needsDetail?: (sourceJobId: string, target?: string | null) => boolean`.

## 3. Report board health to the worker/registry

Dead boards (404/410, BambooHR's redirect to its marketing site, robots.txt opt-outs) are logged once and the
target finishes cleanly, as P07 asks. Today that is only a log line. Proposal:

```ts
/** Optional: called once per target with what the scraper learned about the board. */
reportTarget?: (slug: string, status: { state: "ok" | "empty" | "gone" | "blocked"; openJobs?: number; detail?: string }) => void;
```

The worker could put this in `RunReport` and P04's `verify.ts` could auto-drop `gone`/`blocked` entries. Note
for P04: SmartRecruiters returns `200 {"totalFound":0}` for **unknown** company ids, so "empty" can mean "wrong id".

## 4. Structured location parts on `RawJob`

Most ATS APIs return structured `{city, region, country(ISO2)}`, and P07 flattens them into `"City, Region, Country"`
strings for `RawJob.locations`, which the normalizer then parses back. Suggest an optional hint:

```ts
locationParts?: { raw: string; city?: string | null; region?: string | null; country?: string | null }[];
```

Meanwhile ISO codes go in `extra.country` / `extra.countryCodes` / `extra.countryCode`.

## 5. Salary periods `week` and `day`

Lever (`per-week-salary`, `per-day-wage`) and others publish weekly/daily pay. `Salary.period` has no value for
them, so P07 sets only `salaryRaw`. Suggest adding `"week" | "day"` (INR yearly: ×52 / ×260).

## 6. `applyFormUrl` as a first-class optional field

ATSs expose both a posting page and a direct application form (Lever `/apply`, Ashby `/application`, Workable
`/apply`, SmartRecruiters `?oga=true`). Per P07, `applyUrl` is the official posting page. The form URL is in
`extra.applyFormUrl`; an optional `RawJob.applyFormUrl` would let the UI deep-link to the form.
