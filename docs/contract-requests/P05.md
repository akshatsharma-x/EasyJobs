# P05 · Worker — contract requests

Nothing here blocks P05: the worker already behaves correctly under contract v1.0.0, and items 2–3 are implemented worker-side. These requests are for W1. Items 2–3 also answer P09 #1–2, P10 #1 and P11 #1.

## 1. Root `pnpm-workspace.yaml`: pnpm 12 ignores `onlyBuiltDependencies` (root file — W1)

With pnpm 12.23 (installed here), adding any package that pulls in `tsx`/`vitest` (esbuild) exits with `ERR_PNPM_IGNORED_BUILDS`. `package.json` and the lockfile are still written, and esbuild works without its postinstall, but the non-zero exit will break scripts and CI.

- **Ask:** add the new setting next to the old one (keep the old one for pnpm 10):
  ```yaml
  allowBuilds:
    esbuild: true
    sharp: true
  ```
  `pnpm add --help` on 12.23 confirms that `--allow-build` appends to `allowBuilds`.

## 2. Scraper hooks for sweeps, graceful stops and stats (contract — worker already supports them)

Sweeps close everything a run didn't emit, so a run that sees only part of a listing must never sweep:
- incremental feeds that stop at known ids (P10)
- search results (P11)
- runs that ended on a block page (P11)

Under v1.0.0 a scraper can only return or throw, so these all look like clean, complete runs. The worker currently reads these optional runtime hooks:

```ts
interface Scraper {
  /** false → the worker never sweeps this scraper (incremental feeds, search results). Default true. */
  sweep?: boolean;
}
interface ScrapeContext {
  /** This run saw only part of the listing: no sweep after it. Status unaffected. */
  markIncomplete?(reason?: string): void;
  /**
   * report("partial" | "blocked", { reason, retryAt? }) → RunReport "partial", no sweep, and no rerun before retryAt
   *   ("blocked" without retryAt counts as a failure: backoff + circuit breaker).
   * report({ siteTotal: 2054, … }) → numeric run stats (worker GET /status, JSON logs).
   */
  report?(statusOrStats: "partial" | "blocked" | Record<string, number>, info?: { reason?: string; retryAt?: string }): void;
}
```

- **Ask:** add these to `@easyjobs/contract/node`, bump `CONTRACT_VERSION`, and update the Scraper doc.
- One naming conflict: P09 proposed `report?(stats)` and P11 proposed `report?(status, info)`. The worker accepts both forms under one name. If W1 prefers two methods (e.g. `report(status, info)` and `stats(record)`), the worker change is a few lines in `apps/worker/src/pipeline.ts`.

## 3. Document what `since` and `isKnown` may do (contract docs — P09 #1)

The current wording ("only jobs posted/updated after this") invites scrapers to drop older jobs, and a sweep would then close them. The worker never sweeps after a run that received `since`. It passes `since` only on incremental runs and makes a full run (no `since`) at least every `WORKER_FULL_REFRESH_MINUTES` (60).

- **Ask:** reword `ScrapeContext.since` to: "Hint to skip *work* (detail pages, deep pagination). A run that receives `since` is never swept." Reword `isKnown` to: "Known jobs must still be emitted (as light records); they count as seen."

## 4. Mark light records (contract — P02/P03)

A record emitted for a known job (`isKnown` → `descriptionHtml: null`) carries no description. The merge keeps the stored description. But derived scalars computed by normalize without it could still overwrite better values from the full record: `experienceLevel`, `category`, `summary`, `qualityScore`, skills.

- **Ask:** add `RawJob.light?: boolean`. P03 copies it to `JobInput.extra.light`, and the API's merge skips description-derived fields for light records. The worker passes records through unchanged, so nothing changes in P05.

## 5. Richer `RunReport` (contract — P02 stats / UI)

The worker already computes these per run and shows them on its own `GET /status`, but v1.0.0's RunReport can't carry them:
- raw / valid / invalid / duplicate counts
- inserted / updated / merged / rejected
- spooled
- whether the run was sweep-eligible
- scraper-reported stats

- **Ask:** add optional `stats?: Record<string, number>` and `complete?: boolean` to `RunReport`. P02 stores them in `scrape_runs`. Example uses: coverage and freshness on `GET /v1/stats`, and the per-source table in W1's INTEGRATION.md.

## 6. Sweep keys for sources with complete listings (guidance — scrapers)

`SweepRequest.target` is a required string, so jobs emitted with `target: null` can never be swept and only close via the 21-day rule.

- **Ask (no contract change):** scrapers whose run is a complete listing should set `target`:
  - per-company portals: the registry slug (P09 already does this)
  - complete API feeds (Remote OK, Arbeitnow…): a stable feed key, e.g. the scraper id

  Then closed postings disappear within about an hour instead of 21 days. Incremental or search sources keep `target: null`, plus `sweep: false` once item 2 lands.
