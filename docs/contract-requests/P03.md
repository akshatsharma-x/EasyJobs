# P03 · Normalizer: contract requests

Nothing here blocks P03. Everything works under contract v1.0.0, and the workarounds use `JobInput.extra` or local
types. These are suggestions for W1 (contract and §0.4) and for P02 (the API merge). Items 1, 2, 3a and 4 agree with
asks from P05, P06, P07, P08, P10 and P12.

## 1. Light records and defaulted fields in the merge (contract + P02): agrees with P05 #4, P06 #2, P08

**Problem.** §0.4 says scalar fields come from the highest `SOURCE_KIND_PRIORITY` source with a non-null value. But
`experienceLevel`, `jobType` and `category` are never null; they fall back to `entry`, `full_time` and `other`.

- An ATS record whose title says nothing about seniority would overwrite a blog's evidence-based `fresher`
  (batch 2026, "freshers") with a guessed `entry`.
- A light record (a re-sighting without description) would overwrite stored description-derived fields with weaker
  ones.

**Today:**
- `extra.normalize.defaulted: string[]` lists the fields that hold a default rather than evidence.
- `extra.light: true` is copied from `RawJob.extra.light`/`RawJob.light`. It is also set when the record has no
  description at all.
- `extra.normalize.confidence` gives `{ level, category }` as `high`, `medium` or `low`.

**Ask:**
- `RawJob.light?: boolean`, and `JobInput.light?: boolean`, or document `extra.light` as the convention.
- The merge never lets a **defaulted** value overwrite a stored non-defaulted one, whatever the source priority.
- For light records, the merge keeps the stored description-derived fields: `experienceLevel`, `category`, `skills`,
  `degrees`, `summary`, `descriptionHtml`/`descriptionText` and `qualityScore`.
- Optionally promote `defaulted` to `JobInput.defaulted?: ("experienceLevel" | "jobType" | "category")[]`.

## 2. A shared `DEGREES` constant (contract): agrees with P06 #4 and P12

**Today:** `@easyjobs/normalize` exports `DEGREES` (30 labels). `cleanDegreeList` maps the scrapers' labels onto them
(`Any Graduate`, `Any Postgraduate`, `UG` → Bachelor's, `PG` → Master's, `PGDM` → MBA, `B.A.` → BA, …):

`B.E/B.Tech`, `M.E/M.Tech`, `BCA`, `MCA`, `B.Sc`, `M.Sc`, `BBA`, `MBA`, `B.Com`, `M.Com`, `BA`, `MA`, `Diploma`, `PhD`,
`Any graduate`, `Any postgraduate`, `Bachelor's`, `Master's`, `12th Pass`, `10th Pass`, `ITI`, `B.Pharm`, `M.Pharm`,
`MBBS`, `B.Arch`, `B.Des`, `LLB`, `LLM`, `CA`, `CFA`.

**Ask:** move the list into the contract as `DEGREES` (plus labels if the UI wants different display text). Scrapers
would then emit the same labels and the UI could offer a degree filter. Labels outside the list stay allowed: they are
kept tidy, not dropped.

## 3. §0.4 fingerprint wording (W1)

### a. Rule 1 only for job-specific official URLs: agrees with P06 #3

Blogs often link a careers landing page (`https://www.infosys.com/careers/`, `https://nextstep.tcs.com/campus/`). With
rule 1 as written, `canonicalUrl(landing page)` becomes the dedupe key, so every job linking it collapses into one.

**Today:**
- Rule 1 applies only when the URL is official **and** `isJobSpecificUrl(url)` holds: an ATS job key, a job-id-like
  path segment or query parameter, or a job slug under `/jobs/`.
- `RawJob.extra.applyUrlSpecific: boolean` (P06 emits it) overrides the heuristic.
- Everything else uses rule 2.

**Ask:**
- Amend §0.4 rule 1 to read: "If `applyUrl` is on an official host **and points at a single posting**…".
- Optionally add `RawJob.applyUrlSpecific?: boolean`.

### b. Keep SPA hash routes in canonical URLs

§0.4 says canonical URLs have "no hash". Some portals keep the job id in a hash route, for example Superset's
`https://app.joinsuperset.com/join/#/signup/student/jobprofiles/<uuid>`. Dropping the hash merged 5 different jobs
in real data.

**Today:**
- `canonicalUrl` keeps `#/…` and `#!/…` routes and drops every other hash (`#apply`, `#top`).
- `canonicalJobKey` has a `superset:<uuid>` rule.

**Ask:** amend §0.4 to "no hash, except SPA routes (`#/…`, `#!/…`)".

## 4. Salary periods `week` and `day` (contract): agrees with P07 #5 and P10 #3

`Salary.period` is `hour | month | year`. Weekly pay (Internshala stipends, Lever `per-week-salary`) and daily pay
(`per-day-wage`, "₹500/day") have nowhere to go.

**Today:**
- Both are converted to `period: "month"`: week × 52/12, day × 22 working days.
- `salary.raw` keeps the original text.
- INR yearly = month × 12, so a day is worth 264 per year.

**Ask:** add `"week" | "day"` to `Salary.period`, with fixed INR-yearly factors. Week ×52; for days, P07 suggests ×260,
and normalize would switch from 264 to whatever the contract fixes.

## 5. Confidence and provenance on `JobInput` (contract, optional)

**Today:** `extra.normalize` holds:
- `confidence.{level,category}`;
- `sources.{level,jobType,workMode,experience}` (hint / years / title / description / default …);
- `fingerprintRule`;
- `version`.

**Ask:** optional `JobInput.confidence?: { experienceLevel: "high" | "medium" | "low"; category: … }`. The UI could
then soften low-confidence badges ("Entry level?"), and the merge could prefer high-confidence values (see #1).

## 6. More `KNOWN_TAGS` (contract / P01): agrees with P10 #5

`KNOWN_TAGS` has `off-campus`, `walk-in`, `wfh`, `women`, `diversity`, `pwd`, `urgent` and `suspicious`. The normalizer
also emits:
- **`test-posting`:** ATS test requisitions that leak into public feeds ("DO NOT APPLY - TEST REQ"). There were 3 in
  real data, and they score −80 quality. Suggest the API hides them by default.
- **Scraper hint tags it keeps:** `unpaid` (180 in real data), `part-time` (85), `ppo` (37), `visa-sponsorship` (9).

**Ask:** add these with labels, so the UI can filter on them. Free-form tags would stay allowed.

## 7. Re-normalization (P02, optional)

`extra.normalize.version` (`NORMALIZER_VERSION`, now `1.0.0`) changes whenever rules change.

**Ask:** P02 stores the last RawJob per source (or at least its `descriptionHtml` and hints) next to the job. A
version bump could then re-normalize stored jobs without re-scraping. Otherwise improvements reach a job only when it
is next seen.

## 8. Root `pnpm-workspace.yaml` (W1): same as P05 #1, P06 #7, P10 #7, P11 #5

Every `pnpm --filter @easyjobs/normalize add …` ended with `ERR_PNPM_IGNORED_BUILDS` (esbuild) and a non-zero exit.
The install itself succeeded: `package.json` and the lockfile were updated, and tsx/vitest work.

**Ask:** move the build-approval setting to the form pnpm 12 reads (`allowBuilds`), or run `pnpm approve-builds`
once, so concurrent sessions stop retrying installs that actually succeeded.
