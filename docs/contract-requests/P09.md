# P09 contract requests (custom career portals — `@easyjobs/scraper-bigtech`)

Nothing here blocks P09; everything is handled locally. These are for W1 to consider.

## 1. `ScrapeContext.since` vs. sweeps (correctness — affects every scraper)

`since` is documented as "only jobs posted/updated after this", and P05 sweeps `(source, target)` after every
complete run, closing whatever the run did not emit. A scraper that honours `since` by dropping older jobs therefore
gets all of its older, still-open jobs closed on the next sweep.

- What P09 does: `since` is **not** used to drop jobs. Known jobs (via `isKnown`) are emitted as light records
  (`descriptionHtml: null`, which the merge never writes over a stored value) so sweeps see them as open.
- Request: state in §0.2/`ScrapeContext` docs that `since` may only be used to skip *work* (detail fetches), never to
  shrink the emitted set of a complete run — or have the worker skip the sweep when it passes `since`.

## 2. Optional run stats on `Scraper` (nice to have)

Custom portals report a site-side total ("2,054 jobs in India") that is useful for monitoring coverage. P09 exposes
it as a non-contract `lastRun` property (`listed`, `emitted`, `skipped`, `invalid`, `details`, `deferred`,
`siteTotal`). Request: an optional `ScrapeContext.report?(stats: Record<string, number>)` callback the worker could
include in `RunReport`.

## 3. Registry entries for P09 companies (for P04 / W1)

Each P09 scraper uses `target = id = registry slug` (e.g. `amazon`, `goldman-sachs`, `tech-mahindra`) so the worker
can look up company tags by target. P04 should either use the same slugs with `ats: "custom"` (token = careers URL,
which the worker doesn't feed to ATS adapters) or alias them. The full list, and the companies that turned out to be
plain ATS boards, are in `packages/scrapers/bigtech/README.md` ("Registry notes").
