# P11 · LinkedIn + Naukri — contract requests

Nothing here blocks P11; each item has a working fallback inside `packages/scrapers/portals`. These are for W1, and for P05/P03 where noted.

## 1. Let a scraper report "blocked / partial" without throwing (contract, P05)

The P11 rules say: on 429/999/403 or a challenge page, back off for hours and **end the run gracefully**. The `Scraper` interface can only return or throw, so a graceful stop looks like a clean, complete run to the worker.

- **Today:** every portal job has `target: null` (search results are never a complete listing, so they must never be swept). Blocks are recorded in `packages/scrapers/portals/.state/<portal>.json` (`lastRun.outcome`, `lastBlock`, `blockedUntil`) and logged as one `BLOCKED …` line. This is the same situation as P10 #1.
- **Ask:** an optional `ScrapeContext.report?(status: "partial" | "blocked", info: { reason: string; retryAt?: string })`, which the worker maps to `RunReport.status = "partial"` and shows on `/status`, plus `Scraper.sweep?: boolean` (P10 #1) so `(source, null)` is never swept.

## 2. robots.txt failures should not mean allow-all (contract `createHttpClient`)

`robotsAllows()` treats any robots.txt failure (network error, 5xx, 429) as "no rules", i.e. everything allowed. RFC 9309 §2.3.1.4 says an unreachable robots.txt (5xx or network) means **assume complete disallow**. For LinkedIn, whose robots.txt disallows everything for us, a robots.txt outage would currently open the gate.

- **Today:** P11 runs its own strict gate first (`src/shared/robots.ts`): 2xx → parse; other 4xx → allow; 5xx/network → disallow with a 1 h pause; a block page → back off. Every later request is still robots-checked by the contract client.
- **Ask:** in `robotsAllows`, cache 5xx/network/429 as "disallow all" for a short TTL (for example 10 min), and keep 4xx as "allow".

## 3. Don't retry HTTP 999 (contract `createHttpClient`)

`retryable = … || res.status >= 500` also matches LinkedIn's non-standard **999**, its anti-bot "request denied". Retrying it 3 times within 30 s is exactly what that response asks you not to do. I checked that Node's fetch surfaces 999 as a normal response (`ok: false`).

- **Today:** P11 sends every request with `retries: 0` and handles 429/999/403 itself.
- **Ask:** treat statuses ≥ 600 (and 999 explicitly) as non-retryable, like 403.

## 4. canonicalJobKey / job-board hosts (P03)

- `linkedin.com` (all subdomains such as `in.linkedin.com`) and `naukri.com` must be on the job-board host list, so §0.4 rule 2 applies when `applyUrl` is the portal page.
- Canonical keys: LinkedIn `https://www.linkedin.com/jobs/view/{id}` (P11 always emits this form as `sourceUrl`); Naukri job pages end with `-{jobId}` (`https://www.naukri.com/job-listings-…-251125900001`).
- When the portal exposes the company/ATS apply link, P11 puts it in `applyUrl`, so rule 1 merges the job with the official record. The portal page is always `sourceUrl`, and the discovered URL is also kept in `extra.linkedin.offsiteApplyUrl` / `extra.naukri.companyApplyUrl`. The P11 prompt literally says `applyUrl = /jobs/view/{id}` (and `jdURL → applyUrl`). If W1 prefers that, it's a one-line change in each `map.ts`.

## 5. Root tooling note (W1): pnpm 12 ignores `onlyBuiltDependencies`

Every `pnpm --filter … add …` ends with `ERR_PNPM_IGNORED_BUILDS: Ignored build scripts: esbuild@0.28.2` and a non-zero exit, although the install itself completes: `package.json` and the lockfile are updated, and esbuild works through its platform package. That's misleading for concurrent sessions that retry on failure. `pnpm-workspace.yaml` is a root file I can't edit; running `pnpm approve-builds`, or migrating the setting to the pnpm 12 form, would fix it.
