# Contract requests from P02 (Database + API)

Nothing here blocks Phase 1. The API already behaves as described and stays compatible with contract 1.0.0.

## 1. `SweepRequest.target: string | null`

Scrapers that don't use registry targets (CourseJoiner, Internshala, feeds) emit `RawJob.target = null`. A sweep for them
has no target string to send.
**Now:** the API accepts `target: null` or `""` and matches rows whose target is NULL or `''`.
**Request:** type it as `target: string | null` and document that `null` means "the source's target-less postings".

## 2. `SweepResponse.removed`

The API returns `{ closed, removed }`. `removed` is the number of (source, sourceJobId) rows that the sweep detached;
`closed` counts only the jobs left with no source at all. The worker's run summary can use both.
**Request:** add `removed: number` to `SweepResponse`.

## 3. "Did you mean" / fuzzy flags on `JobsSearchResponse`

Typo correction (`amazn` → amazon) and the trigram fallback are reported in the headers `X-Search-Corrected: amazn%3Damazon`
and `X-Search-Mode: fuzzy`, both exposed via CORS.
**Request:** optional fields `corrections?: Record<string, string>` and `fuzzy?: boolean`, so the UI can show
"Showing results for *amazon*".

## 4. Company profile fields in `JobInput`

`CompanySummary.hq` and `careersUrl` can't be filled from `JobInput`. Today they come from `@easyjobs/registry`, loaded
dynamically when it exists, and only for companies we already have jobs for.
**Request:** optional `companyHq?: string | null` and `companyCareersUrl?: string | null` in `JobInput`, filled by
normalize from the registry entry. Alternatively, an ingest route that upserts `CompanyTarget[]`.

## 5. Type-ahead flag in `SearchQuery`

`parseSearchQuery` trims `q`, so "react " (word finished) and "react" (still typing) look the same. The API therefore
always prefix-matches the last token (`react` also finds `reactjs`).
**Request (low priority):** keep a trailing-space signal, for example `prefix?: boolean`.

## 6. Already implemented for P05's requests #4 and #5

* Light records: when `JobInput.extra.light === true`, the merge never touches description-derived fields
  (level, experience range, category, summary, description).
* `RunReport.complete?` / `RunReport.stats?` are accepted and stored in `scrape_runs`.

Once W1 adds these to the contract (`RawJob.light`, and the `RunReport` fields), no API change is needed.

## 7. Small clarifications

* `FacetBucket.value` for `batch` is the year as a string ("2026"). Selected values are always returned, with count 0
  when nothing matches, so chips stay visible.
* `totalPages` is capped at 500, because `parseSearchQuery` clamps `page` to 500.
* `JobListItem.locations` display strings are built like this: "City, CC" when a city is known; otherwise the raw
  string; plus "Remote" when `isRemote` is true and no string already says so.
* `GET /v1/companies` without `q` lists only companies with open jobs. With `q` it lists every match, ordered by openJobs
  descending. The default `pageSize` is 24 and the maximum is 100.
