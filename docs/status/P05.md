# P05 · Scheduler and ingestion worker — status

**Package:** `@easyjobs/worker` (`apps/worker/**`). **State:** done. Typecheck is clean and **62/62 tests** pass offline in about 4 s. `once --source demo --dry-run` works, and `start` was run against the fake ingest API, including an outage, replay, SIGHUP and restart. The full design is in `apps/worker/README.md`.

## Summary

- **Discovery** of everything at runtime, with no hard imports:
  - every `packages/scrapers/*/src/index.ts`
  - `packages/normalize` `normalizeJob`, used only if it loads **and** passes a smoke test; otherwise `src/fallback-normalize.ts`
  - `packages/registry` `companies` + `findCompany`, used if it exports ≥ 1 valid company; otherwise `fixtures/companies.sample.json`: 10 real boards on greenhouse/lever/ashby/workday, verified live on 2026-11-25
  - Broken packages are reported and never crash the worker. Re-scan runs every 10 min and on SIGHUP.
- **Scheduler**:
  - one task per feed scraper, and one per (ATS scraper, registry target) with priority cadence 15 m / 1 h / 24 h
  - stratified spread plus jitter; priority aging, so p3 can't starve
  - global and per-scraper concurrency, per-task timeout, AbortSignal on shutdown
  - exponential backoff, and a circuit breaker (5 failures → 6 h pause → half-open trial)
  - persisted state and a single-scheduler lock
- **Pipeline**: known ids → scrape → validateRawJob → normalize (with the registry company) → validateJobInput → dedupe → gzip batches of 200 → sweep (complete full runs only, with a safety guard) → RunReport. An ordered on-disk **spool** with in-order replay covers API outages, with a dead-letter guard so one poison request can't block it.
- **Interfaces**:
  - CLI: `start`, `once`, `list`, `replay`, plus the dev tools `fake-api` and `bench`
  - HTTP: `GET /health`, `GET /status`, `POST /run/:source` (x-ingest-key)
  - one concise summary line per task, structured with `LOG_FORMAT=json`

## Decisions

1. **Sweeps only follow *complete full* runs.** That means no error, no limit, no rejected batch, and **no `ctx.since`**. A scraper that honours `since` emits only a subset, and sweeping that subset would close live jobs. So runs are incremental (`since` = start of last success − 10 min) with a **full refresh at least every 60 min** (`WORKER_FULL_REFRESH_MINUTES`). The first run and manual triggers are always full. Net effect: closed postings disappear within about an hour.
2. **Sweep safety guard.** If a target suddenly reports 0 jobs, or under 20 % of a previous ≥ 20, the sweep waits for the next complete run to confirm it. This stops one bad response (empty body, rate-limit page) from mass-closing a board. Every *listed* id counts as seen, valid or not.
3. **Sweep targets.**
   - ATS tasks sweep their own target. A RawJob with `target: null` on an ATS task is filled in with the task's slug.
   - Feed scrapers sweep each non-null `RawJob.target` they emit. Targets that vanish are swept after the guard confirms them.
   - Jobs with `target: null` can't be swept, because `SweepRequest.target` is required. They rely on the 21-day staleness rule (see contract requests).
4. **Real normalizer/registry must prove themselves.** The normalizer must pass a smoke test (sample RawJob → valid JobInput); the registry needs ≥ 1 valid entry. Otherwise the fallback is used, so a half-built sibling can never zero out ingestion. Fallback output is tagged `extra.normalizedBy: "worker-fallback"`.
5. **Spool ordering.**
   - While anything is spooled, every new request queues behind it, so jobs → sweep → report always apply in order.
   - Spooled cases: network errors, timeouts, 5xx/429 after retries, and **401/403/404** (a misconfigured key or a missing route loses nothing). Other 4xx → the batch is dropped and reported. 413 → the batch is split.
   - During shutdown everything is spooled immediately and replayed at the next start.
6. **Spread.**
   - ATS targets (hundreds per ATS host) are spread over min(interval, 60 min). The 60-min cap means daily targets also start within the first hour.
   - Feed scrapers are staggered over ≤ 5 min: each hits a different host, so a longer spread would only delay first data.
   - After the first run: `start + interval × (1 ± 10 %)`. Overdue tasks after a restart are re-spread, not fired at once.
7. **What counts as a failure** (for backoff and the breaker): the scraper threw or timed out with 0 valid jobs, or *every* job was invalid. Partial runs, API outages and shutdown aborts don't count. A scraper that ignores its AbortSignal is detached, so its slot is freed.
8. **One owner per ATS.** If two scrapers both declare e.g. `greenhouse`, the first discovered (package order) gets the targets, so no board is scraped twice. Every scraper shares one `createHttpClient`.
9. **The demo scraper** is scheduled only when no real scraper exists (`WORKER_DEMO=auto`) and is always available via `once --source demo`. Its data is unmistakably fake: `.example` domains, a "synthetic" notice, and the `demo` tag.
10. **Lenient input handling, always reported.**
    - Scraper modules may export `scrapers`, a default array, or a single Scraper.
    - Unknown `handlesAts` values are dropped.
    - Missing nullable RawJob fields are coerced to null, and a wrong `source` is corrected. Every fix-up is logged as a warning, so W1 can chase the scraper.
11. **Zero new runtime dependencies** besides `tsx`: node:http, node:zlib and node:util only. `once` never writes schedule state; only `start` does.
12. **Sibling requests are honoured now, worker-side, without a contract change** (P09 #1–2, P10 #1, P11 #1). Details: README, "Scraper extensions".
    - `Scraper.sweep = false` → never sweep that scraper.
    - `ctx.markIncomplete?.(reason)` → no sweep for this run.
    - `ctx.report?.("partial"|"blocked", { reason, retryAt })` → RunReport `partial`, no sweep, and no rerun before `retryAt`.
    - `ctx.report?.({ stats })` → `/status`.
    - Passing `since` never leads to a sweep (P09 #1), as in decision 1.
13. **Dead-letter guard.** A spooled request that fails 5× in a row while `GET /health` is OK goes to `.spool/dead-letter.jsonl`. This covers a payload-specific API bug that always 500s, which would otherwise block the strict FIFO forever. Only network errors and 5xx count. A wrong key (401/403), a missing route (404) or a 429 affects every item, so those items stay spooled with a "check INGEST_API_KEY" hint. It applies to the background replayer in `start`.

## Known gaps

- **Re-scan reloads only entry modules.** It re-evaluates a changed `src/index.ts` (cache-busted import), but modules that file imports stay cached until restart. New packages, fixed entries and registry data loaded by the registry's entry module are all picked up.
- **Light records** (`isKnown` → `descriptionHtml: null`) are sent as-is. If normalize derives level/category from the description, a light record may overwrite better values unless the API's merge guards it (contract request 3).
- **Cross-process staleness:** if a `once` process spools while `start` runs and the API is down, its leftover segment is adopted later and may replay after newer direct sends. This is rare and self-heals at the next sweep. Two `start`s are prevented by the lock.
- **Fallback normalizer is deliberately naive:** a small city/skill vocabulary, no salary-string parsing, and a level default of `mid` when nothing is known. Its fingerprints match §0.4 for Greenhouse/Lever/Ashby/Workday and canonical URLs, but can differ from P03's for other ATSs (switching normalizers can create a few duplicates in dev data).
- **Workday `openJobs` is null** in the sample registry: its unfiltered `total` caps at 2000.
