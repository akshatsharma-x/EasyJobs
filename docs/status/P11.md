## Summary

- Two `job_board` scrapers in `packages/scrapers/portals`: `linkedin` and `naukri`, both with `intervalMinutes: 60`. Both are **disabled unless `ENABLE_LINKEDIN=1` / `ENABLE_NAUKRI=1`** (`isEnabled`). The worker discovers them through `src/index.ts` (`scrapers` plus the default export).
- They are fully built: parsers for listings and details, hint mapping, a rotated keyword plan, 4–6 s pacing, per-run caps from env, capped detail fetches for unknown ids only, block detection (429/999/403, edge "Access Denied", auth wall, CAPTCHA/bot pages), and an exponential backoff measured in hours (2 h → 4 h → … ≤ 7 d) that is persisted and ends runs gracefully.
- **Live result (2026-11-26): both are blocked, so 0 jobs.**
  - **LinkedIn**: `robots.txt` has `User-agent: *` → `Disallow: /`, and *every* named crawler group (Googlebot etc., 41 of them) has `Disallow: /jobs-guest/`. §0.8.6 requires obeying robots.txt for HTML pages, so the scraper reads robots.txt, logs the matching rule and stops: 1 request per run, re-checked every 24 h. No `/jobs-guest/` URL was ever requested, including during development.
  - **Naukri**: the Akamai edge returns `403 Access Denied` to plain HTTP (robots.txt, the search page, the search API) and to vanilla headless Chromium, with and without our bot token. The page never even makes its data request. Per the prompt ("challenged too → ship disabled with evidence") it ships disabled; when enabled, one denied request triggers the backoff.
- Full evidence, with timestamps and Akamai reference ids, is in [`packages/scrapers/portals/README.md#evidence`](../../packages/scrapers/portals/README.md#evidence). It can be re-checked with `pnpm --filter @easyjobs/scraper-portals probe --browser` (≤ 4 requests).

## Decisions

1. **robots.txt over the endpoint list.** LinkedIn's guest endpoints are HTML and robots-disallowed for every agent. The code is complete, but the runtime refuses, and there is deliberately no override switch.
2. **A strict robots gate of our own**, on top of the contract client. Unreachable or 5xx means assume disallow (RFC 9309); a robots.txt served as a block page counts as a block.
3. **`retries: 0` on every portal request.** The contract client would otherwise retry 429, and 999 too (as a "5xx"), within seconds. A block must instead end the run and start an hours-long backoff.
4. **Pacing is measured from the end of the previous request**, process-wide per portal, so consecutive runs stay paced too.
5. **The backoff is persisted** in `packages/scrapers/portals/.state/<portal>.json` (git-ignored). During a backoff a run sends zero requests, and Naukri doesn't launch a browser. A clean run resets the strikes. To force a retry, delete the file.
6. **Graceful means return, not throw**, after emitting whatever was already fetched. Every job has `target: null` (a search window is not a complete listing), so the worker never sweeps portal jobs, and freshness uses the §0.4 job-board expiry. See contract request #1.
7. **Naukri goes through vanilla headless Chromium** (Playwright as an *optional* dependency with a dynamic import) and reads the response the page itself receives. We never call the API ourselves or forge `nkparam`. The UA is Chromium's own plus our bot token. Each run uses a fresh context: no cookies carried in, nothing persisted, images/fonts/media not loaded.
8. **The official apply URL is preferred over the portal URL** when the detail exposes it (contract: "official company/ATS URL whenever known"), which lets §0.4 rule 1 merge the job with its ATS record. The portal URL is always `sourceUrl`, and the discovered URL is also kept in `extra`. This deviates from the prompt's literal `applyUrl = /jobs/view/{id}`; it's a one-line change per `map.ts` if W1 disagrees.
9. **Conservative hints.**
   - LinkedIn seniority: only Internship → intern, Entry level → entry, Director/Executive → executive. Associate and Mid-Senior are left to the normalizer.
   - Without a detail, the query's single f_E code supplies the level; "Internship" employment type always → intern.
   - Naukri: the structured salary is used only when visible and ≥ ₹10,000/yr; years come from "a-b Yrs".
10. **No personal data.** LinkedIn's poster / "Meet the hiring team" and Naukri's recruiter name, email and phone are never read. Tests check this.

## Known gaps

- **0 live jobs from either portal** while the blocks above stand.
- The parsers are built on *reconstructed* fixtures (LinkedIn's guest markup as publicly documented; Naukri's API JSON from public descriptions). They have never seen live data, so expect some selector or field fixes on the first successful live run. Real captures in the fixtures: Naukri's three denial pages and the reduced LinkedIn robots.txt.
- Naukri page-2 URLs (`-jobs-2`) and the `/jobapi/v\d+/(search|job)` patterns are assumptions.
- Concurrency protection is per process (two processes would each pace themselves, but not each other).
- I couldn't run the normalizer on `out/*.fixtures.jsonl` yet, because P03 has no `index.ts`/CLI so far. W1: `pnpm --filter @easyjobs/normalize run cli packages/scrapers/portals/out/linkedin.fixtures.jsonl`.

  1. a way to report a partial or blocked run without throwing;
  2. robots.txt failures shouldn't mean allow-all;
  3. don't retry 999;
  4. job-board hosts and canonical keys for P03;
