# P02 · Database + API — status

**Done.** `@easyjobs/db` (Drizzle + Postgres/PGlite) and `@easyjobs/api` (Hono on Node) implement every §0.5 route with the
exact contract shapes. `pnpm --filter @easyjobs/api dev` serves them against PGlite with seed data. Typecheck and tests
are green on PGlite and on real Postgres. At 100k jobs on Postgres, `/v1/jobs` p95 is under 150 ms in every scenario
measured, including 10 saturating connections with all caching disabled (136 ms).

Owned paths: `packages/db/**`, `apps/api/**`, `docker-compose.yml`, `.data/` (runtime).
Also written: this file and `docs/contract-requests/P02.md`.

## How to run

```bash
pnpm install
pnpm --filter @easyjobs/db seed                # ~2,000 synthetic JobInputs through the real upsert path (PGlite: .data/pglite)
pnpm --filter @easyjobs/api dev                # http://localhost:4000 · docs at /docs · OpenAPI at /openapi.json
pnpm --filter @easyjobs/db test && pnpm --filter @easyjobs/api test
TEST_DATABASE_URL=postgres://localhost:5432/postgres pnpm --filter @easyjobs/db test   # same suite on a real server
pnpm --filter @easyjobs/api bench -- --db postgres --url postgres://…/easyjobs_bench   # or --db pglite (seeds 100k if needed)

docker compose up -d db                        # optional Postgres 17 on :5433
DATABASE_URL=postgres://easyjobs:easyjobs@localhost:5433/easyjobs pnpm --filter @easyjobs/api dev
```

* Migrations run automatically on API, seed and migrate start. Concurrent instances serialize on an advisory lock.
* `seed` flags: `--count N --seed S --batch 500 --reset --via-api --pglite-dir DIR`. If a running API holds the PGlite
  lock, seed falls back to `POST /v1/ingest/jobs`.

## Benchmarks (`apps/api/bench`, autocannon)

Method:
* **Load generation:** the API runs in a child process; autocannon runs in the parent, so load generation and serving
  don't share an event loop.
* **Workload:** a deterministic, realistic `/v1/jobs` mix, with 40 % popular head and 60 % long tail of 4,000 URLs:
  * 8 % landing page
  * 32 % filter browsing
  * 45 % text search, often combined with a location or level filter
  * 15 % typos and prefixes
  * plus pagination and the newest/salary sorts
* **Percentiles:** p50/p95/p99 are exact over every response; autocannon itself only reports p97.5.
* **Run shape:** 3 s warm-up, then 20 s per scenario (10 s for suggest); rate limiting is off.
* **Cache settings:** "cache off" sets `CACHE_TTL_MS=0`, which disables every response and memo cache. That is the worst
  case, where every request does all of its database work.
* **Machine:** Apple M5 Pro (18 cores), Node 22.23.

* Ingest through the real path: Postgres about 1,450 inputs/s; PGlite about 680 inputs/s at 100k, and 1,400/s for the

## Decisions

1. **Merging** follows §0.4 using per-field-group provenance (`field_prio`). Groups that must stay consistent move
   together: salary with its INR values, experience min/max, description html/text. `category: "other"` counts as empty.
   A sighting re-opens the job, and then the freshness rules still apply, so an expired posting stays closed.
2. **Job id** is an 11-character base36 hash of the fingerprint, so URLs stay stable across DB rebuilds. Collisions are
   re-salted. If a (source, sourceJobId) pair shows up under a new fingerprint, the source moves to the new job and the
   old job is re-evaluated, closing it if no source is left.
3. **The search vector** follows the spec's weights. I added a weight-C "meta" field (cities, states, remote/hybrid,
   type/level words, department, tags, batches, and English title stems) so that queries like "bangalore", "remote",
   "fresher" or "engineering" work without the UI converting them into filters. A `search_head` (the vector without the
   description) stays inline for ranking, and a trigger maintains both vectors only when their inputs change.
4. **Relevance** is `ln(ts_rank(head) + 0.03) + rank_base`, where `rank_base = posted_epoch/τ + ln(boosts)`. With
   τ = 14.4 days, ordering by `rank_base` equals ordering by exp-decay × boosts at every instant, so relevance without
   `q` is an index order.
5. **The query parser** implements websearch syntax per term, and each term becomes `websearch_to_tsquery` in both the
   `simple` and `english` configs, OR-ed with its synonyms. The last token also matches as a prefix. When nothing
   matches, typos are corrected from a title/company/skill vocabulary with a trigram index, and as a last resort a
   trigram match runs on lower(title)/lower(company).
6. **Postgres performance:**
   * Text-conditioned statements run with seq and index scans disabled (`set_config` in a transaction). The planner
     can't see detoast cost and otherwise evaluates `@@` row by row.
   * `toast_tuple_target=128` plus `PLAIN`/`MAIN` storage keeps the heap at about 1.4 KB/row, with hot columns first in
     the row.
   * `max_parallel_workers_per_gather=0` for API sessions, because a search already fans out across statements.
7. **Facet engine (deviation from the wording "run facet queries in parallel"):**
   * **Why:** on 100k jobs, Postgres spends about 200 ms of CPU per broad uncached search on facet aggregation, which
     caps throughput near 40 req/s.
   * **Default (`FACET_ENGINE=memory`):** an in-memory columnar index (dictionary-encoded typed arrays of open jobs)
     computes all disjunctive facets, the total, and the page order in one pass taking a few ms.
   * **Postgres's role:** text matching and scoring (one GIN statement per distinct text, memoized), plus a
     primary-key fetch of the page rows.
   * **Reference engine:** the spec's design, parallel SQL facet statements, remains the reference and the fallback
     (while the index builds, or with `FACET_ENGINE=sql`). Tests require identical facets, totals and page ids from
     both engines.
   * **Freshness:** local writes reach the index immediately through an overlay; other instances get changed ids over
     `NOTIFY easyjobs_changed`; a full rebuild runs every 120 s.
8. **Caching:**
   * 20 s LRU with single-flight and refresh-ahead.
   * Keys are normalized: list order, text case, aliases.
   * Facet statements are memoized by the filters they actually apply, so toggling one filter reuses the others.
9. **Ingest validation** is strict for everything `validateJobInput` checks, and lenient for soft fields: they're
   trimmed or truncated, invalid optional URLs/dates/salaries become null, unknown company tags are dropped, and missing
   optional keys are defaulted. One bad item never rejects the batch.
10. **Companies listing:** `GET /v1/companies` without `q` lists only companies with open jobs.
    Profiles (hq, careers URL, tags) are enriched from `@easyjobs/registry` when it exports `companies`; this is
    checked at startup and every 6 h.
11. **Single-process guard for PGlite:** a pid lock file `.data/pglite.lock` produces a clear error instead of a
    corrupted directory.
12. **Light records (P05 request #4):** when `JobInput.extra.light === true` (a re-sighting of a known job without its
    description), the merge never updates the description-derived fields: level, experience range, category,
    summary and description. It still counts as a sighting, and the flag itself is not stored.
13. **Richer RunReport (P05 request #5):** `POST /v1/ingest/runs` also accepts optional `complete: boolean` and
    `stats: Record<string, number>` and stores them in `scrape_runs` (migration `0004_run_stats`). Malformed values
    are dropped; they never reject the report.
14. **Unchanged re-sightings** skip the row write. `last_seen_at` is refreshed at most hourly, as a HOT update (there is
    no index on it).

## Known gaps / notes for W1

* **pnpm 12 ignores `onlyBuiltDependencies`** from `pnpm-workspace.yaml`. Every `pnpm add` therefore exits 1 with
  `ERR_PNPM_IGNORED_BUILDS`, although the packages do install, and esbuild works through its platform package. W1 should
  move the root config to pnpm 12's build-approval setting.
* **Port 4000 was taken on this machine** by an unrelated local process (an `outbox` backend) during development. I
  left it alone and verified the API on `API_PORT=4010`. The default stays 4000 (§0.7).
* **Per-process indexes:** the suggest and facet indexes live in each API process. The facet index measured about
  21 MB for 96.7k open jobs (7.5 MB heap plus 13.3 MB typed arrays). One Node process handles about 200 uncached
  searches/s; beyond that, scale out — LISTEN/NOTIFY keeps instances in sync.
* **Cross-instance freshness:** another instance's sweep or expiry reaches this instance's facet index through
  `NOTIFY easyjobs_changed`, with the 120 s rebuild as the backstop.
* **Benchmark config:** the Postgres numbers come from Homebrew's default configuration. `docker-compose.yml`
  (Postgres 17) ships tuned settings (shared_buffers 512 MB, jit off, SSD costs).
* **Benchmark artifacts on this machine** (safe to delete; a bench run recreates them):
  * `.data/pglite-bench`: 1.8 GB, the 100k PGlite database.
  * `easyjobs_bench` on the local Homebrew Postgres: 884 MB. Remove it with `dropdb easyjobs_bench`.
  * Raw results: `apps/api/bench/results/postgres-97908-2026-11-25T23-35-57-138Z.json` and
    `pglite-100026-2026-11-25T23-38-17-931Z.json`.
* **Contract requests:** target-less sweeps, `SweepResponse.removed`, did-you-mean fields, company profile fields in
  `JobInput`, and a type-ahead flag; details in `docs/contract-requests/P02.md`.
