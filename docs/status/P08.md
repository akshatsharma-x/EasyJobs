# P08 · Enterprise ATS scrapers — status

Package: `packages/scrapers/ats-enterprise` (`@easyjobs/scraper-ats-enterprise`). Full endpoint and
response-shape notes are in its [README](../../packages/scrapers/ats-enterprise/README.md).

## Summary

Nine `Scraper`s, one per enterprise platform, all `kind: "ats"` with `handlesAts` set and driven by
`ctx.targets` (§0.6 tokens): **workday, oracle, eightfold, jsonld** (fully built; endpoints verified
live — Workday's CLI run is blocked from this machine by a Cloudflare challenge, see below), plus
**successfactors, phenom, avature** (best-effort, verified live) and **icims, taleo** (best-effort, built
on the public layouts; no live customer reachable — see gaps). Every endpoint was checked
live on 2026-11-25/26 UTC. Shared machinery covers politeness, back-off, anti-bot detection, schema drift
(zod per item), `isKnown` light records, per-run detail budgets, and incomplete-run signalling so a
partial listing never triggers a sweep.

- `pnpm --filter @easyjobs/scraper-ats-enterprise typecheck` ✅
- `pnpm --filter @easyjobs/scraper-ats-enterprise test` ✅ — 167 offline tests (7 files) on trimmed real
  responses, plus 7 `LIVE=1` smoke tests in `test/live.test.ts` (6 run live and pass; Workday not re-run
  here, see the Workday note).
- CLI: oracle, eightfold, jsonld, successfactors, phenom and avature produce valid RawJobs for all their
  fixture targets (0 invalid). Workday: see *Workday and Cloudflare* below.

## How to run

```bash
pnpm --filter @easyjobs/scraper-ats-enterprise scrape --scraper oracle --limit 40          # all fixture targets of one adapter
pnpm --filter @easyjobs/scraper-ats-enterprise scrape --scraper workday --target nvidia --limit 20
pnpm --filter @easyjobs/scraper-ats-enterprise test
LIVE=1 pnpm --filter @easyjobs/scraper-ats-enterprise test -- live
```
Output goes to `out/<scraper>.jsonl` (the contract CLI). With several targets, `--limit` is split
evenly so every fixture target is sampled. Fixture targets: `src/fixtures/targets.ts` (22 real,
verified companies).

## Decisions

1. **Never truncate a listing with `ctx.since`.** The worker sweeps after complete runs; a `since`-cut
   listing would close live jobs. Work is saved through `isKnown` instead.
2. **Known jobs → light records** (list data, `descriptionHtml: null`, `extra.light: true`), no detail call.
3. **Detail budget per run; over-budget unknown jobs are deferred**, not emitted light: never stored → no
   sweep impact, and they get a description next run (a light record would make them "known" forever).
   `*_OVERFLOW=light` flips this. Limited runs (`ctx.limit`) stop paging once the budget is spent.
4. **Incomplete ⇒ no sweep.** Partial listings yield what they have and then signal: worker hooks
   `report("blocked", {retryAt})` / `report("partial")` / `markIncomplete()` when present (apps/worker
   supports them), else `IncompleteRunError`. Nothing emitted still throws, so real failures reach the
   breaker. Board 404/410/422 on page 1 = gone → 0 jobs, normal finish (as P07).
5. **Zero discovered job URLs on a JSON-LD site is an error**, never "everything closed".
6. **Anti-bot challenges are not bypassed** (no UA/TLS changes, proxies, cookies); detected by
   `cf-mitigated` / challenge pages and treated as a block.
7. **Politeness above the contract client:** process-wide limiter per source; Workday and Eightfold share
   one gate across tenants because their limits are per client, not per tenant. Contract retries are
   disabled (`retries: 0`) so back-off is source-wide and challenges are never retried.
8. **Workday worker-type partition** when a complete "Job Type" facet exists → structured
   `internship` / `intern` / `fresher` hints for every job, early-career buckets get detail budget first.
9. **IDs derivable before details:** `workday` `{tenant}:{JR-suffix}`, `oracle` `{pod}:{Id}`,
   `eightfold` `{domain}:{positionId}`, page sources `{host}:{id-like segment}`.
10. **Only structured hints** (employment/worker/workplace types, structured salary); keyword inference
    from titles/descriptions is left to `@easyjobs/normalize`.
11. **Sitemap sources keep a small page index** (`.cache/state/`) so known jobs can be emitted as light
    records without refetching; a known URL that can be neither fetched nor recalled ⇒ incomplete run.

## Workday and Cloudflare

**Status: implemented and tested offline on real responses; the CLI run from this machine is blocked.**

What happened (UTC, 2026-11-25/26), all from one residential IP:

| Time | Client | Result |
|---|---|---|
| 22:00–22:35 | curl, exploring 12 tenants (~75 requests, ≤ 1 rps) | all 200 |
| 22:25 | first Node CLI run, Intel, 2 in flight ≈ 1.3 req/s | 7 jobs emitted, then `429` + `cf-mitigated: challenge` |
| 22:31–22:46 | Node | challenged from the first request, on every tenant (Intel, Workday, Mastercard, ADI) |
| 22:40 | curl, same IP, same moment | 200 — also with `--http1.1` and with Node's default headers |
| 22:47 / 22:49 | Node | one 200, then challenged again |
| 23:11, 00:26 | Node after 22 and 75 quiet minutes | challenged on the first request; curl at 23:12 → 200 |

The first challenge followed a burst; after that the classification held regardless of rate (even after
75 quiet minutes) while curl from the same IP was never challenged — so Workday's Cloudflare edge keys on
the Node.js client fingerprint plus IP reputation. Changing the client fingerprint or IP would be
evasion, so the adapter does not try. It does what the rules ask:

- detects the challenge (`cf-mitigated: challenge` / "Enable JavaScript and cookies to continue"),
  never retries it, and records a 15-minute no-request window for **all** Workday tenants in the process
  (the 00:26 run made one API request, plus the contract client's robots.txt check, for six targets);
- reports `blocked` with `retryAt` = +60 min to the worker (no failure count, no sweep);
- keeps a zone-wide gate (1 in flight, 3 s between requests) so a fresh IP is not pushed into a challenge.

What this means for integration (W1/W2): run the worker once from the deployment host; if Workday answers
normally there, the adapter works as tested (list → partitions → details). If it is challenged too, Workday
coverage needs either a Cloudflare-friendly arrangement with the source or reliance on other paths
(Phenom/Radancy front-ends such as careers.adobe.com and www.careers.philips.com already return the
underlying Workday apply URLs, which merge with Workday records by fingerprint).

## Known gaps

- **Workday from Node.js may be challenged by Cloudflare** (above). The adapter stays polite and stops
  cleanly, but throughput depends on the deployment's IP reputation; keep `WORKDAY_DELAY_MS` high and use
  `extra.workdayCountry` for India-focused targets to cut request volume.
- **iCIMS and Taleo are not live-verified**: every `careers-*.icims.com` portal I tried returned iCIMS'
  "Site Not Found", and the only resolvable Taleo section was "Career Section Unavailable". Both adapters
  follow the public layouts and fall back to the sitemap/JSON-LD engine; they need a real customer token
  from the registry to confirm.
- **Eightfold v2 `location=` filter** was verified on PCSX (PayPal) only; v2 tenants were rate-limited
  when I tried it.
- **Light records cannot be upgraded later:** `isKnown` is a boolean, so a job first stored without a
  description (overflow=light, or a detail error) never gets one. Contract request below.
- Avature: Bloomberg pages carry no posting date; Deloitte's JSON-LD has a blank address and cards say
  "Multiple Locations". SuccessFactors/EY microdata has no department/employment type.
- Big-tenant first runs are long by design (NVIDIA ≈ 150 list pages + 300 details at 3 s ≈ 20 min); the
  per-target budget (25 min) ends the run as incomplete rather than overrun.
- Country filters: `extra.workdayCountry` (as specified) or the generic `extra.country` (Workday, Oracle,
  Eightfold). The registry (P04) does not set these yet, so production lists are global by default.
